# Sonar architecture and privacy contract

## Implemented boundaries

React renders the responsive shell, direct messages, contact search, pinned history, browser pairing, fingerprints, and voice controls. Zustand separates account and conversation state. API calls use the same origin; Vite proxies HTTP and sockets in development. Socket identity comes from a verified HTTP-only JWT cookie. Authenticated sockets join server-selected account rooms; multiple connections receive message and pin events.

The message service accepts versioned ciphertext envelopes only. Records contain participant IDs, ciphertext, IV, version, timestamps, pin state, and expiry. The rebuilt client has no plaintext message or attachment upload path. Account and relationship metadata remain visible to the service.

## Communities and channels

Private communities support up to 32 members and 30 text channels. The owner creates channels and generates 24-hour invite links. The server stores only the invite hash; generating a replacement revokes the previous link. Join updates membership atomically and increments its revision. All channel routes check current membership. All members see future channel messages; there are no private subchannels or moderation roles yet.

For each message, the sender encrypts a separate copy for every current member, including themselves, using the existing browser-held identity keys. Channel ID is bound into AES-GCM authenticated data, preventing channel ciphertext from being decrypted as a direct message or moved between channels. The server requires an exact recipient set and matching membership revision. It returns and emits only the requesting recipient's envelope. New members do not receive envelopes for old messages and cannot read or pin them. Pinned history does not bypass this boundary. Existing static-key and trust-on-first-use limitations still apply; this is not MLS and does not provide forward secrecy.

Names and membership are unencrypted metadata. Invite links are bearer credentials, so share them privately. Non-owners can leave; owners can remove another member or transfer ownership to a current member. Owners must transfer before leaving, including when they are the only remaining member. Removal and ownership transfer revoke the active invite. A new owner can issue a fresh invite to allow a removed user to rejoin. Removal is not a permanent ban.

Channel sends run in a MongoDB transaction that writes the community document and inserts the message atomically. Membership changes update that same document and increment its revision. Conflicting sends retry against the changed revision and fail closed when stale. This requires Atlas or a replica set; the isolated test database and optional local launcher both use single-node replica sets. Owner-only writes also include the current owner in their update filter, preventing stale owner requests after transfer. Broadcast recipients are reloaded after the message write, excluding members already removed at that check.

Removal blocks future message envelopes and API access. A request or delivery already in progress may finish before removal; previously received ciphertext/plaintext cannot be revoked. Rejoining can restore access to old envelopes originally addressed to that account. It does not grant messages sent while absent. Remaining members receive public keys for historical message authors so retained history still decrypts after an author leaves. These author details contain display names and public keys, never email or passwords.

Realtime removal clears the active client conversation and cached plaintext in the community store. Community list refresh and forbidden detail refresh also clear access when an event was missed. This is client cleanup, not a guarantee against recipient copies or suspended/offline devices.

Direct and channel history use descending `(createdAt, _id)` cursor pagination and return chronological pages to the client. The default page size is 50, with a validated maximum of 100. The cursor contains only a timestamp and record ID; it grants no access. Every page independently applies participant/membership, envelope-recipient, and expiry filters. Pin-only queries are paginated independently, so older pins are reachable. Legacy callers receive an array; callers opting into `page=true` receive `{ messages, hasMore, nextCursor }`. Pins and messages remain encrypted throughout retrieval. Local database tests cover timestamp ties, complete traversal, malformed cursors, expiry, and access control without using Atlas.

Client history merges overlapping pages by message ID, retains realtime updates, and rejects results belonging to an older conversation request. Loading older messages preserves the viewport anchor; incoming messages auto-scroll only when the user is already near the bottom. Drafts are scoped to direct-message recipients or community/channel IDs and held only in a bounded memory store. They are never sent to the backend or saved in localStorage/IndexedDB. Signout clears all drafts; membership loss clears that community's drafts. Reload clears them. These drafts do not provide persistence or recovery across devices.

## Encryption

Each account has one ECDH P-256 identity. Participants derive an AES-256-GCM conversation key with a random 96-bit IV per message. Authenticated additional data binds version and ordered participant IDs. Decryption errors fail closed. Device-local contact key pinning blocks changes after first use; compare the displayed fingerprint outside Sonar to verify a contact.

### Recovery key and multi-device backup

So that the web client and the desktop app can open the same conversations, the private key is stored on the server **only in encrypted form**, locked with a recovery key the user saves (`frontend/src/lib/keyBackup.js`, `desktop/src/key_backup.rs`, `backend/src/lib/keyBackup.js`). Format v2:

- recovery key = 15 random bytes (120 bits), shown as 24 Crockford base32 characters; created on the device and never uploaded
- wrapping key = HMAC-SHA256(recovery key, `sonar-recovery-wrap-v2:<accountId>`)
- ciphertext = AES-256-GCM(PKCS#8 private key), random 12-byte IV, AAD `sonar-key-backup-v2:<accountId>:<public key>`; after decryption the client checks the private key matches the published public key
- reset proof = HMAC-SHA256(recovery key, `sonar-recovery-proof-v2`); the server stores only SHA-256(proof) and cannot derive the wrapping key from it

A new device signs in, then unlocks the backup with the recovery key. **Forgot password** (`POST /api/auth/recover`, rate limited) takes the email, proof and new password, signs out other sessions, and the client immediately issues a fresh recovery key because the server has now seen the old proof. No email service is involved. Changing or replacing a recovery key requires the current password. Both clients are tested against `desktop/tests/recovery-fixture.json`.

Older formats migrate automatically: a v1 backup (wrapped with a password-derived key) is replaced by v2 at the next password sign-in, and the user is shown a recovery key. Accounts with only a non-exportable browser key must use **Privacy & device → Turn on multi-device access**, which rotates the key; the old key stays retired in that browser so earlier messages remain readable there.

Contacts compare a **safety code** (the SHA-256 of the public key in groups) in person or on a call. It is not a biometric fingerprint. A changed key blocks sending until the user confirms the codes match.

Limits: this protects against the server operator and database theft only while the client code is honest. The web client is delivered by the server, so a malicious operator could ship altered JavaScript; the signed desktop build is the stronger option once code signing exists. A v1 backup in old database backups stays password-wrapped. Losing both the recovery key and every signed-in device loses encrypted history, and losing the recovery key means a forgotten password cannot be reset.

This uses standard primitives but is a custom, unaudited protocol. Static keys provide neither forward secrecy nor post-compromise security. Trust on first use does not protect initial discovery against a malicious server. Compromised devices, browser extensions, or servers delivering malicious JavaScript can defeat browser encryption. Keys are origin-specific; changing deployment origin changes access. Non-exportability prevents key export through the API, not malicious code invoking decryption. Concurrent first-use identity and contact-key creation are serialized across tabs. The first observed contact key is still unauthenticated and must be checked independently.

Reference: [Web Crypto specification](https://www.w3.org/TR/webcrypto/).

## Retention

Unpinned messages expire seven days after creation. History and pin operations filter expired records immediately. MongoDB TTL deletes expired records asynchronously. Pins set expiry to null; unpinning starts a fresh seven-day period. Either participant can change pin state. The UI checks expiry on its 30-second refresh interval; suspended clients may retain decrypted content until resuming.

Backups, operator exports, recipient copies, screenshots, and external recordings are outside this mechanism. Production backup retention must follow the same requirement. Existing plaintext documents are excluded from new history but are NOT automatically encrypted or destroyed. Explicitly decide how to remove legacy data and backups before rollout. Ensure MongoDB creates the TTL index. Do not claim historical data was encrypted or deleted by this change.

## Voice

Direct RTCPeerConnection audio uses WebRTC DTLS-SRTP encryption. Socket.IO relays transient offers, answers, and ICE candidates. There is no MediaRecorder, call database, server media processing, or recording endpoint. Tracks stop on call end, disconnect, failure, or unmount. Unanswered calls time out after a minute. ICE candidates queue until the remote description is ready; local candidates wait until the server accepts the offer/answer. Disconnected transports have a ten-second grace period before cleanup. The UI supports mute, deafen (muting both playback and local transmission), elapsed time, and retrying browser-blocked audio playback.

An in-memory call registry binds each call ID to its two accounts and selected sockets. It rejects cross-call signals, busy users, offline recipients, and stale answers. Answering in one tab stops ringing in other tabs. Hangup, unanswered timeout, and participating socket disconnect release the call. Signaling is limited per socket. No call registry survives process restart. Multi-process deployments will need shared transient call coordination and appropriate Socket.IO routing.

No external STUN/TURN provider is contacted by default. Configure operator-controlled ICE services through backend STUN_URLS, TURN_URLS, and TURN_SHARED_SECRET. The authenticated, no-store voice-config endpoint generates coturn-compatible HMAC-SHA1 credentials with anonymous random usernames and one-hour expiry; it never returns the shared secret. The browser can request relay-only mode; VOICE_RELAY_ONLY can require it server-side. Relay-only mode fails closed when TURN is missing. Direct calls expose peer network information to participants. Active calls and rooms refresh the ICE server configuration before credential expiry and retry temporary failures. This does not force an ICE restart or prove existing allocations survive expiry; long-duration relay calls still require real-server testing. Signaling is authenticated but media fingerprints are not independently verified; malicious signaling or modified application code remains a risk. Participants can record on their own devices.

Voice settings and microphone tests are browser-local and memory-only. The test computes an input-level meter via Web Audio without recording, transmitting, or playing back microphone data. Input capture and AudioContext are stopped on test end, settings close, or unmount. Device names are enumerated after the user grants microphone permission. Changes apply to subsequent calls. The isolated browser suite uses fake audio inputs in two separate contexts, verifies actual inbound WebRTC audio bytes, and checks microphone-state and track cleanup; this does not replace a physical-device or cross-network/TURN test.

Speaker settings use HTMLMediaElement.setSinkId for permitted audio-output selection, with feature detection and system-default guidance when unsupported. selectAudioOutput is offered only when available; otherwise the interface enumerates permitted devices. Output selection and volume apply to the remote-audio element at call setup and through a live settings subscription. A failed explicit selection pauses/blocks playback and asks the user to choose a valid output rather than silently reverting to default. Output device IDs and preferences are held in memory, never sent to the server. Device unplugging and operating-system routing remain browser/platform dependent.

The speaker test synthesizes a short WAV chime locally and plays it through the same output/volume helper; it never opens the microphone. Its Audio element and blob URL are released on stop, completion, device change, or unmount. Browser checks cover actual test playback, no added capture tracks, and active-call volume changes. Routing unit checks cover explicit device IDs and failure without fallback. Physical speaker audibility and platform-specific device choosers still require manual hardware testing. Reference: [Audio Output Devices API](https://www.w3.org/TR/audio-output/).

TURN reference: [coturn authentication configuration](https://github.com/coturn/coturn/wiki/turnserver).

Reference: [WebRTC security architecture](https://www.rfc-editor.org/rfc/rfc8827.html).

## Community voice rooms

Channels have a `type` of text or voice; legacy channels default to text. Only owners create either type, and voice channels cannot use text message endpoints. A voice room uses a full mesh of browser RTCPeerConnections, capped at six accounts. Each browser captures a single local microphone stream and attaches its tracks to each peer connection. Media uses WebRTC transport encryption directly between participants (or via the configured TURN relay); the backend never mixes, receives, records, or stores audio. This is not an SFU implementation and has not been independently audited.

Room occupancy is held in memory. Join/list/signal/status operations require current community membership and a voice channel. Each joining account receives a new session ID bound to its selected socket; both peer session IDs are checked on signals so a departed session cannot inject into a later join. Room capacity and per-account exclusivity are checked again after asynchronous user lookup. Direct calls and rooms share occupancy guards. New joiners initiate offers to existing participants to avoid offer glare. ICE candidates queue until descriptions and signaling are ready. Mute/deafen affect local transmission, and deafen also mutes remote playback. Speaker preferences apply to every room playback element.

Membership mutations reconcile room occupancy and remove unauthorized participants; every signaling/status request also rechecks membership. A removed member receives an ejection event, and remaining peers close that member's connections on the next room-state update. Audio already received or in flight cannot be erased, and modified clients can record or retain previously received content. A room may keep the microphone open even when its participant is alone until that participant leaves. Changing views does not leave a room. Closing/disconnecting the active socket ends its room participation. Reconnection requires explicit rejoin rather than automatically requesting microphone access.

Snapshot metadata includes participant names, account IDs, ephemeral session IDs, mute/deafen state, and room occupancy. It is visible to community members and the service. There is no persistent room session or call history. This coordination is process-local and requires shared transient state/routing before multi-instance deployment. Independent peer media identity verification, automatic peer reconnection, real-server long-call TURN validation, and larger room scalability remain future work. Three-context local browser tests verify real inbound RTP from both other peers, controls, navigation, removal, and capture cleanup; network/hardware validation remains necessary.

## Account security and passkeys

Passkey support uses SimpleWebAuthn registration and discoverable authentication with required user verification and resident credentials. Enrollment and removal require a current password. The service stores credential public keys, counters, names, and transports; it never receives biometric data or the authenticator private key. Registration/authentication challenges are persisted with five-minute expiry, bound to HTTP-only same-site cookies, and atomically consumed once. Verification checks challenge, exact configured origin, relying-party ID, user handle, user verification, signature, and counter. Account security changes and credential updates serialize through transactions; enrollment caps at ten keys. Removal revokes sessions. Passkey requests have a process-local IP limiter and password-confirmation operations share the account password-attempt limiter.

In development only, the IP-address preview opens a dedicated localhost page for the WebAuthn ceremony. Messages between the windows check the exact origin, source window, and request ID. The child receives only public credential options and returns only the public signed response; it never receives account sessions or encryption keys. There is no key migration. Production runs the ceremony on the configured HTTPS origin. Signing in from a different chat origin/browser can authenticate the account but cannot unlock its paired encryption identity; the existing pairing restriction still applies.

References: [SimpleWebAuthn server](https://simplewebauthn.dev/docs/packages/server), [browser](https://simplewebauthn.dev/docs/packages/browser), and [WebAuthn relying-party scope](https://web.dev/articles/webauthn-rp-id).

Account settings support display-name editing, password changes, a read-only email, the browser identity fingerprint, and an individual session list. New logins include a random JWT session ID; only its SHA-256 digest, account ID, method, and dates are stored. The server checks current, unexpired records on HTTP requests, socket handshakes, and incoming socket events, and a TTL index removes expired records. Individual revocation removes the record and emits a disconnect to that session's room on the current process. Existing signed JWTs without session IDs remain valid until expiry or account-wide revocation and cannot be individually listed. Idle sockets also recheck their session and token expiry every 15 seconds; failed or stalled checks disconnect after a five-second timeout. Across processes this is not immediate: sockets can still receive events until the next check completes, and database polling adds load. A shared real-time adapter remains necessary for immediate cross-process revocation and delivery. Session records must not be treated as a device inventory; no IP or user-agent is collected. Password changes compare the current bcrypt hash, atomically replace it, and increment an account session version. JWT authentication checks the version on every HTTP request and socket handshake; incoming socket events recheck the stored version. Password changes and logout emit session revocation and disconnect account sockets. Logout is explicitly account-wide. Older JWTs without a version are treated as version zero for compatibility until that account revokes sessions. Private encryption keys are unaffected. Profile/auth responses omit password hashes and internal session versions.

The password endpoint allows ten attempts per account per fifteen-minute window in a bounded process-local limiter. Deployments with multiple backend processes need a shared limiter store. Login and signup have IP limits of 30 and 10 requests per 15 minutes respectively, including successful attempts. Passkey authentication operations have separate limits. `MONGO_SHARED_AUTH_LIMITS=true` switches these and password confirmation to atomic shared MongoDB counters keyed by HMAC of the scope, client key, and fixed window. An expiry index removes stale counters asynchronously; database or index failure fails closed. Shared mode requires the same database, JWT secret, and synchronized clocks. The additional broad passkey request limit remains process-local. Express does not trust forwarded addresses by default; `TRUST_PROXY_CIDRS` can identify operator-controlled proxies, which must overwrite forwarded headers. Incorrect proxy trust can enable spoofing. Fixed windows permit boundary bursts, and distributed abuse can consume storage before TTL cleanup. Passwords for new accounts and password changes require 10 characters and at most 72 UTF-8 bytes, matching bcrypt's input boundary. Existing shorter passwords remain accepted at login.

## Required production work

1. Adopt an audited messaging protocol with forward secrecy, verified identity, recovery, and multiple devices. Use a reviewed group protocol such as MLS for channels.
2. Extend existing member management with moderation roles, channel permissions, account bans, and community deletion. Encrypt attachments before object storage.
3. Provision and validate operator-controlled TURN, verify long calls, add independent call identity verification, and scale group voice beyond the six-person mesh. The credential endpoint, relay-only preference, and small community voice rooms are implemented; a relay service is not bundled.
4. Configure shared authentication limits, add broader abuse controls and quotas, and propagate socket revocations across backend instances. Individual tracked sign-in sessions are implemented without collecting device metadata.
5. Add live MongoDB and multi-browser tests, accessibility review, reconnect/race testing, and professional security review.
6. Establish backup deletion rules, remove legacy plaintext with operator authorization, and verify TTL indexes before opening registration.

Free use is a product policy, not cost-free infrastructure. There are no billing paths or paid features.

## Community and channel deletion

Only the owner may delete a channel or community. MongoDB transactions remove the community/channel and its stored messages together, including pinned messages; channel deletion retains at least one text channel. Membership/channel changes serialize against transactional channel-message creation. Voice-room state is reconciled and participants are disconnected. Clients receive updates, discard affected drafts, and select an available channel. Backups and client-saved copies are outside this deletion operation. MongoDB replica-set support is required.

## Moderator permissions

Communities store moderator account IDs alongside membership. Owners alone grant and revoke the role, and moderators may remove ordinary members only; owner and moderator targets are protected. Membership and role conditions are rechecked atomically on removal, preventing a demoted or departed moderator from using a stale authorization snapshot. Role changes increment the membership revision so in-flight sends refresh their recipient state. Leaving, removal, and ownership transfer remove obsolete moderator assignments. Owners and moderators may ban members within the same hierarchy; an atomic update removes membership, adds the banned account, invalidates the invite, and increments the revision. Invite joins atomically exclude banned accounts. Only owners can list or remove bans; unbanning also revokes the active invite and does not restore membership. The ban list is capped at 500 accounts and excluded from ordinary community responses. Account bans do not prevent alternate accounts. Private channels are not implemented. Roles and membership are visible metadata.

## Native desktop

`desktop/` is a native Rust client built with Iced (software rendering via tiny-skia; no browser engine, WebView, Tauri or Electron). It reproduces the web interface screen for screen: the same layout, colour tokens and text sizes matching `frontend/src/index.css`, the bundled Poppins font, and the web's Lucide icons (generated from `frontend/node_modules/lucide-react` by `desktop/scripts/generate-icons.mjs`). It speaks the same protocol as the browser, so a desktop user and a web user share one account, one key and the same conversations.

- **Accounts:** sign up, password and Windows passkey sign-in, session restore, individual session sign-out, profile, password change, passkey management.
- **Encryption:** the v1 P-256 ECDH + AES-256-GCM envelopes, checked byte-for-byte against Web Crypto fixtures, for direct messages and per-member channel envelopes. Contact keys are trusted on first use and a change blocks sending until the typed fingerprint matches, as on the web.
- **Messaging:** history with cursor pagination, pins, replies, reactions, deletion, drafts per conversation, 7-day expiry, live delivery over Socket.IO, and offline unread indicators from server candidates plus local read positions.
- **Communities:** create, join by invite, channels, rename/delete, members, moderators, bans, ownership transfer, leaving.
- **Voice:** direct calls (offer/answer/ICE over `call:signal`, interoperable with the browser) and community voice rooms (a mesh of up to five peers over `voice:room-signal`, each remote speaker decoded and mixed separately). Audio is Opus over DTLS-SRTP. As in the browser, the peer's DTLS fingerprint comes from the SDP relayed by the authenticated signalling server; it is not independently verified.
- **Local storage** (`%LOCALAPPDATA%\Sonar`): the identity key and session cookie are protected with Windows DPAPI for the current user. Contact-key pins, read positions and audio preferences are plain JSON. DPAPI does not protect against malware running as the same user.

Memory, measured once on the development machine: about 36 MiB working set / 10 MiB private at the sign-in screen, and 28 MiB / 10.5 MiB signed in with conversations loaded (release build, window minimized). These numbers vary by machine.

The previous Portuguese-language preview UI, which only used the experimental Matrix path, is kept unbuilt in `desktop/legacy/`. The Matrix modules remain for the probes in `desktop/examples/`.

Voice-room locks are persisted on voice channels and checked on join. Owners and moderators can disconnect a current participant via socket signaling after checking community permissions and participant session ID; the lock or kick is not a community ban. Cross-instance voice state and authorization propagation remain unsupported.
